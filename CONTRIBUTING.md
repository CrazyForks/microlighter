# Contributing to MicroLighter

Thanks for your interest in improving MicroLighter! This is a small,
dependency-free library, and contributions of all sizes are welcome — new
grammars, new themes, bug fixes, and docs.

## Getting started

You'll need [Node.js](https://nodejs.org) 18 or newer (see `.nvmrc`).

```sh
git clone https://github.com/davatron5000/microlighter.git
cd microlighter
npm install
```

Common tasks:

```sh
npm run build   # bundle src/ into dist/ and print a size report
npm test        # rebuild, then run the Playwright end-to-end tests
npm run size    # print the size report only (read-only)
npx serve docs  # preview the demo at http://localhost:3000
```

## Project layout

```
src/
  index.js          # side-effect-free programmatic API (default export)
  microlighter.js   # side-effectful auto-runner (builds microlighter.min.js)
  highlight.js      # the TextMate-grammar -> CSS Custom Highlight tokenizer
  grammars/*.js     # one ES module per language grammar
  themes/*.css      # one theme per file, styling ::highlight() pseudo-elements
scripts/
  report-size.mjs   # size report + optional homepage stat updater
docs/               # the self-contained GitHub Pages demo site
dist/               # build output (generated; not committed)
test/               # Playwright end-to-end specs (*.spec.pw.js)
```

`dist/` is generated by `npm run build` and is git-ignored. The demo in `docs/`
loads a vendored copy of the build from `docs/microlighter/`, which the build
refreshes automatically.

## How highlighting works

MicroLighter tokenizes code with TextMate grammars, then maps each grammar
**scope** (e.g. `keyword.control.js`) to a small set of **categories**
(`keyword`, `string`, `comment`, …) in `src/highlight.js`. Themes then style
those categories via the `::highlight(category)` pseudo-element. There are no
per-token `<span>`s — ranges live in the CSS Custom Highlight registry.

### Adding a grammar

1. Add `src/grammars/<language>.js` exporting a TextMate grammar as the default
   export (it must include a `scopeName`).
2. If the language is commonly referenced by an alias (e.g. `ts`, `yml`), add it
   to the `aliases` map in `src/index.js`.
3. Add a code block for it to `docs/index.html` so it's covered by the demo and
   the tests.

### Adding a theme

1. Add `src/themes/<name>.css` scoped to `[data-syntax-theme="<name>"]`, styling
   the `::highlight(...)` categories. Use existing themes as a template.
2. Add an `@import` for it in `src/themes/index.css`.
3. Add the theme to the `<select>` in `docs/index.html`.

Keep page-chrome styling (backgrounds, borders) out of theme files — themes
should only define syntax colors. The demo page derives its own chrome.

## Size budget

Payload size is a core feature. The build fails if the minified bundle's gzip
size exceeds the `sizeLimit` in `package.json`. If a change legitimately needs
more room, call it out in your PR so we can discuss the budget.

## Tests

End-to-end tests in `test/*.spec.pw.js` drive `docs/index.html` in a real
browser with Playwright. Please keep them green and add coverage for new
behavior. `npm test` rebuilds before running so tests always reflect your
current code.

## Updating the homepage size figure

The headline gzip number on the demo homepage is **not** updated automatically.
When a change moves the bundle size, refresh it explicitly and commit the diff:

```sh
npm run docs:update-homepage-stats
```

## Style

Code style is enforced by `.editorconfig` (2-space indent, LF, UTF-8). Match the
surrounding code: modern ES modules, no build-time transpilation, and no runtime
dependencies. Comment only where intent isn't obvious.

## Submitting changes

1. Fork and create a branch.
2. Make your change with tests.
3. Run `npm test` and confirm the size budget passes.
4. Open a pull request describing the change and any size impact.
